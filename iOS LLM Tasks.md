This ecosystem already has routing (`ProviderGatewayKit`), structured decoding (`StructuredOutputKit`), cost metering (`TokenMeterKit`), caching (`ResponseCacheKit`), and schema-validated tool dispatch (`ToolRegistryKit`) — but nothing that actually *drives* a multi-step tool-calling loop for a plain-text (non-tool-calling) model. That gap matches the "agent-loop/orchestration" candidate from this series' own list.

**Package built today:**
- **AgentLoopKit** — a bounded, host-driven ReAct loop (`AgentLoop` actor) over `ProviderGatewayKit.LLMSession` + `ToolRegistryKit.ToolRegistry`: a pluggable `AgentResponseParser` turns raw model text into an `AgentDecision` (tool call vs. final answer — the bundled `JSONToolCallParser` recognizes `{"tool": ..., "arguments": {...}}`, everything else is the final answer verbatim), dispatched tool calls go through `ToolRegistryKit` for real schema validation, and a pluggable `AgentPromptStrategy` folds the result back into the next turn. Every run returns a complete `AgentTranscript` with a typed `AgentHaltReason` (`.finalAnswer` / `.maxStepsExceeded` / `.toolDispatchFailed` / `.parseFailed`) — `run(initialPrompt:)` only throws for a genuine session/router transport failure, never for "the agent didn't converge." 21 tests, 100.00% line/function/region coverage on every file, 0 SwiftLint violations (tool-verified).
  https://github.com/rajatslakhina/agent-loop-kit

**Design note — why this doesn't duplicate `ProviderRouter`'s built-in tool-calling:** `ProviderGatewayKit.ProviderRouter` already transparently drives *provider-native* tool-calling round trips when a provider's capabilities say `supportsToolCalling: true` (against its own minimal, string-only, unvalidated built-in `ToolRegistry`). `AgentLoopKit` is for the other, equally common case — exactly this ecosystem's own simulated/scripted providers — where the model only emits plain text and "decided to call a tool" has to be inferred from it, with the call itself going through `ToolRegistryKit` for real `JSONSchema` validation. It also generalizes the exact hand-rolled loop `runToolCallingScenario` in the shared demo was already writing out by hand for a *single* tool call — `AgentLoopKit` makes that a reusable actor that can chain multiple dependent tool calls.

**Coverage-gate design fix worth flagging:** hit a genuine "impossible to reach 100% coverage" wall from a `precondition(maxSteps > 0, ...)` in `AgentLoop.init` — Swift's `precondition` trap branch can't be exercised without crashing the test process, and a fresh coverage run of `foundation-model-provider-gateway` itself confirmed this is a pre-existing, silent, never-flagged gap across the whole series (`ProviderRouter.swift` sits at 90.48%, `LLMRequest.swift` at 75.00% — both solely due to their own `precondition` calls, despite the log never calling this out before today). Rather than repeat that pattern, redesigned `maxSteps` to clamp to `max(1, maxSteps)` instead of trapping — a real, testable, and arguably better public-API behavior — which is what let `AgentLoopKit` reach a literal, tool-verified 100.00%. Not fixed in the older packages today (out of scope for a light maintenance pass on other people's already-released public API), but worth a deliberate look in a future run with a larger time budget.

**Shared demo:** `llm-ecosystem-demo` extended with a sixth scenario — `AgentLoop.run(initialPrompt:)` chains two dependent `get_weather` calls (Austin, then Boston) before the model converges on a comparison answer, driven through the self-hosted provider identity (diversifying from the cloud identity the fifth, hand-rolled tool-calling scenario already uses). `TokenMeterKit` meters every step of the returned `AgentTranscript` entirely after the fact — `AgentLoopKit` never needs to know `TokenMeterKit` exists, demonstrating real package decoupling. **Package completed today:** **RealtimeSessionKit** — an actor-based session that outlives the connection carrying it. `RealtimeSession` (actor) makes five guarantees it can evidence: (1) **at-least-once outbound** — an outbox holds every enqueued event until the server acks it *by id*, and replays unacked events in original send order on resume; (2) **per-conversation ordering** — inbound events apply strictly in server sequence, and an event that would skip ahead is **refused, not applied**, leaving the cursor put so that resuming from it makes the server backfill the gap (accepting it would silently lose whatever preceded it); (3) **two-layer inbound dedup** — a bounded window of recent ids catches immediate redelivery, and the cursor catches replays whose ids already aged out of that window; the second layer exists *precisely because* the first is bounded, which is the design insight the demo proves rather than asserts; (4) an **explicit resume-vs-cold-start fork** via `ResumeDecision`, because a cold start invalidates conversation state and a resume does not; (5) **full-jitter exponential backoff under a bounded retry budget**, since an unbounded reconnect loop turns a dead session into a battery drain while the app never learns the conversation is gone. **Package built today:** **IdempotencyKit** — an actor-based guard giving at-most-once side effects under at-least-once delivery. `IdempotencyGuard.execute(key:payload:now:using:)` runs the executor at most once per key and makes four refusals it can evidence:

1. **Concurrent duplicate.** The in-flight key set lives on the guard actor, not in the store. This is the design decision the package turns on: the store is reached with an `await`, so a reservation written there leaves a window in which a second caller reads "not present" before the first writes. Check-and-claim happens in one uninterrupted actor turn, which is the only way the rejection is exact — the same insight `BatchInferenceKit` used on 07-27's first pass to make `peakActive` a true high-water mark rather than a sample.
2. **Key reuse with a changed payload.** Every record stores a `KeyFingerprint` of the payload's canonical form; a mismatch throws `keyReuseConflict` rather than replaying a result that answers a different question.
3. **Indeterminate outcome.** `FailureMode` splits a failure into `.notApplied` (provably nothing happened — the key is released for a real retry) and `.indeterminate` (it may have landed — the key is frozen until `resolve(key:as:)`). An executor error that is *not* an `EffectFailure` is classified `.indeterminate`, because an unclassified error is not evidence that nothing happened. This is the difference between a guard that is safe and one that merely looks safe.
4. **Empty key.** Refused rather than treated as a wildcard.

Two further choices worth recording. Key derivation hashes the payload's **sorted-field canonical form with FNV-1a, not Swift's `Hasher`** — `Hasher` is seeded per process, so a derived key would not survive the crash-and-restart that is precisely when deduplication matters. **Package built today:** **SchemaMigrationKit** — `SchemaRegistry`, an actor that owns contracts, versions, and the steps between them, making five guarantees it can evidence:

1. **Every hop is validated against the schema that hop promised.** A step that claims to produce v2 and forgets a field v2 requires fails *at that step*, named: `postconditionViolated(contract: search.tool, step: "v1 -> v2", version: v2, violations: [missing required field 'locale'])`. 2. **No shortcut edges.** Paths walk *adjacent* registered versions only; a `v1 -> v3` step is refused at registration, because it would let a v1 payload reach v3 without ever being checked against v2. 3. **The source payload is checked before anything runs.** Migrating garbage produces garbage that merely looks migrated.
4. **Loss is declared per step, and refused by default.** A step says what it discards; a path that drops anything throws `lossyMigrationRefused` unless the caller passes `allowingLoss: true`, and the dropped fields land in the audit trail. Loss is declared rather than inferred from a schema diff on purpose: a diff can tell you a field is gone, but only the author knows whether it was folded into another field or genuinely discarded.
5. **Deprecation is asymmetric.** A version past its sunset tick is refused as a migration *target* while migrating *away* from it still works — which is the entire point of sunsetting, and a symmetric check would strand exactly the payloads you are trying to rescue.

**Package built today:** **ToolAuthorityKit** — `AuthorityBroker`, an actor that sits between the step that picks a tool call and the step that dispatches it, making five guarantees it can evidence:

1. **Deny by default, and the denial names one axis.** With nothing granted, nothing is allowed. Each refusal is `noCapability` / `actionNotGranted` / `resourceOutOfScope` / `provenanceExceedsGrant` / `grantExpired` / `grantExhausted` — never a generic "denied". 2. **Scope is matched on path segments, never on characters.** `.subtree(orders)` admits `orders/1234` and refuses `orders-archive/1234`. `ResourcePath` stores segments rather than text precisely so the oldest bug in scoped authorization cannot be written.
3. **Authority shrinks with the provenance of the arguments.** This is the deterministic answer to indirect prompt injection, and the reason the package exists. Injected text in a retrieved document reaches the model no matter what; what the broker can do is refuse to let a call whose arguments were *shaped by* that document exercise a capability that only admits operator-authored input. 4. **An approval covers one exact call, once.** `Approval` carries an FNV-1a digest over principal, tool, action, resource and arguments. This is aimed straight at the documented weakness of human-in-the-loop: it degrades under approval fatigue and collapses entirely when a signature can be reused after the arguments change. The digest deliberately excludes the proposal's `id` (two proposals that would do the same thing should satisfy the same signature, and a signature must not be dodged by re-issuing under a fresh id) and deliberately includes the principal. `AuthorityDecision` has **three** cases, not two — folding `approvalRequired` into `denied` leaves callers unable to tell "never" from "not yet", and callers that cannot tell them apart either block forever or learn to auto-approve.

**Package built today:** **GroundingKit** — `GroundingVerifier`, an actor that checks an answer against the passages it was given, one claim at a time, making five guarantees it can evidence:

1. **A verdict per claim, never a score for the answer.** `grounded: 0.72` is not something a caller can act on. Every claim gets its own `SupportLevel`, its own supporting span, and its own citation issues, so the report names the sentence to delete, re-retrieve for, or re-cite.
2. **Support is evidenced by a quotable span, not by a number.** Every `supported` verdict carries the source id and the character range inside that source that backs it. A scorer returning a high score with no span is treated as `unsupported` **regardless of the score** — which is the one case a stub scorer exists in the test suite to prove.
3. **Silence and denial are different verdicts.** `unsupported` means the sources say nothing, which is a *retrieval* problem; `contradicted` means a source says otherwise, which is a *model* problem. Collapsing both into "ungrounded" sends you to fix the wrong half of the pipeline. `notEvaluable` is a third distinct outcome, for a segment carrying no content terms at all — a Markdown rule, "Here is what I found." Naming it is honest about what the code actually determined; calling it `unsupported` would report a connective sentence as a hallucination.
4. **Grounding and attribution are computed separately.** `level` comes from the **whole** evidence set; `citationIssues` come from the sources that claim actually cited. A sentence can therefore be `supported` *and* carry a `citationDoesNotSupport` — true, but attributed to the wrong document, which is a different repair. The two citation failures are also kept apart: `unknownSource` means the model invented a document, `citationDoesNotSupport` means it misread a real one.
5. **The gate decides, and refuses by default.** `.refuse` / `.strip` / `.annotate`. Stripping removes every claim a violation names — including a citation-only one, because a claim you cannot attribute is a claim you cannot publish — and **refuses rather than returning an empty answer**, since an empty revision reads as success. The unsupported allowance is a budget for the whole answer rather than a per-claim pardon: once blown, every unsupported claim is named, because "one of these four is over budget" is not actionable.

Both moving parts are seams (`ClaimSegmenting`, `ClaimSupportScoring`), and the scorer **measures without judging** — it reports a score, the best passage and any conflict, and the verifier alone applies the threshold, which is what lets one scorer serve a strict legal gate and a lenient chat gate unchanged. The default `LexicalOverlapScorer` scores **recall over the claim** rather than a symmetric similarity, because a long passage that happens to contain the claim is a perfectly good source and Jaccard would punish it for length. Conflicts are found two ways: a **polarity** flip (`does not include` against `includes`, with `n't` expanded first so `doesn't` and `does not` are one assertion) and a **quantity** the source does not carry (`10 GB` against `2 GB`, with numbers canonicalised so `10`, `10.0` and `010` are one value). An `EvidenceSet` refuses to be empty on purpose: scoring an answer against nothing would mark every claim unsupported, which renders a retrieval outage as a hallucinating model — the wrong bug to send someone looking for. The failures are quantified and public: a research-agent product burning roughly **$48,000 in fourteen hours** from one misbehaving customer session, and a set of agents that entered an infinite loop and ran **eleven days** to a **$47,000** bill. What neither lacked was dashboards. Enforcement has converged on being **token-aware** — caps on TPM and cost rather than RPM, because token consumption per request varies wildly and one agent chaining twenty steps looks identical to twenty cheap calls. The recommended mechanism is a **reserve-commit** pattern that walks from the agent scope up to the tenant root and denies if any ancestor is exhausted. And one line in the material named the gap directly: *almost no one builds estimates around "what if this agent runs N loops of M steps each"* — which is exactly what a nested run budget answers.

**Non-overlap checked against the five nearest packages rather than assumed.** `TokenMeterKit` records what a call cost and prices it, which is accounting — by the time its numbers exist the money is committed, so it cannot refuse anything. `RetryPolicyKit`'s `RateLimiter` is a token bucket over *request rate* with no principal, no cost, and no reservation; it answers "may I send now", not "does this holder have budget left". `ToolAuthorityKit` authorises *actions on resources*, and its `Grant.maxUses` counts uses of a grant rather than tokens or money in a window. `BatchInferenceKit` bounds in-flight count for one batch under a single global limit, with no competing principals to be fair between. `IdempotencyKit` is a different axis entirely. Nothing in the twenty-two owned **the decision about whether the next request may run at all**. `git ls-remote` confirmed `quota-governor-kit`, `admission-control-kit`, `token-quota-kit` and `budget-governor-kit` were all free before starting.

**Package built today:** **QuotaGovernorKit** — `QuotaGovernor`, an actor that holds an estimate against every budget on a request's path, lets the request run, and settles the difference. Five guarantees it can evidence:

1. **Reserved is not spent.** An open reservation holds its amount on every scope in the path, so two concurrent callers cannot both pass a check only one of them fits through; check-and-claim happens in one uninterrupted actor turn, the same insight `IdempotencyKit` turned on. Every check runs before any ledger is touched, so a refusal leaves no partial hold behind.
2. **The amount held is a policy, not the estimate.** `ReservationPricing` is the seam the package exists around: `ExactPricing` holds what you predicted, `HeadroomPricing(percent:)` holds integer-percent more. Headroom does not enlarge the budget, it enlarges the *hold* — unused slack is refunded on settlement, and the request that would have overrun is refused up front instead. The demo proves the difference on one pair of numbers: against a 1,200-token cap, exact pricing lets a 1,000-token estimate through and then breaches at 1,400 actual (−200, arrears), while 25% headroom refuses it before it runs at `1200 left, 1250 requested`.
3. **A refusal names the scope and the axis.** The quota walk is **outermost-first**, so when several scopes are over, the one named is the tenant rather than the run — because if the tenant is out, raising the run's budget is not the fix, and a message naming the run sends somebody to do exactly that. Money is an integer count of **microcents**, not a `Double` of dollars: a budget decision is a comparison, and floating point makes it approximate at the one moment it has to be exact.
4. **Refund and overrun are computed per axis, never netted.** A response can land *under* on tokens and *over* on money in the same request — a price change does that — and one signed number would report neither. This is not a hypothetical: the shared demo's step 1 hits it with real metered figures (below).
5. **A governor cannot refund reality.** When a request spends past its hold the money is gone before the governor hears about it, so `settle` always succeeds and reports what it found: `refunded`, `overrun`, `breached` (outermost first), `quarantined`. A breached scope goes into arrears and `remaining(on:)` returns a **negative** number rather than zero, because a debt the next window has to absorb is not a balance of nothing. All the governor can still do is refuse the next request.

**Design decisions worth recording.**
- **A path must start at a root.** A caller allowed to reserve against `run-42` on its own would skip the tenant scope entirely, which makes the tenant cap advisory rather than real. `resolve` refuses a path whose first scope has a parent, and the error names both the expected and the actual parent.
- **Open holds deliberately survive a window roll.** They belong to requests that are still running; releasing them at the boundary would hand back budget the governor is still on the hook for and then subtract it again on settlement. Only settled spend clears. `WindowTests` asserts exactly this: after the roll, `spent` is zero and a 400-token hold is still there, so a 700-token request is refused at `600 left`.
- **`forgive` lifts the freeze and nothing else.** The tempting version also zeroes the arrears, and it was rejected: that rewrites spend history inside a word that sounds administrative. Raising a ceiling is `grant`, a separate call with its own audit event, so a mid-window top-up is something you can find in the log later. The demo walks all four resulting states — arrears, frozen, forgiven-but-still-spent, granted-and-working — because they are four different problems.
- **Fair share is computed against actual demand**, `max(1, limit / children currently asking)`, recomputed as children arrive and leave. The honest limit is documented rather than papered over: **slots already granted are never clawed back**, because they are backing requests that are already running, so a newcomer at a full parent gets `concurrencyExhausted` and waits. Fair share bounds new grants; it does not rewrite history.
- **Two choices made to keep the code honest rather than to chase the coverage number.** `ScopeLedger.rollWindow` returns the new window index as an `Int?` instead of a `Bool`, because the `Bool` version forced a `windowIndex ?? 0` in the audit line whose `nil` arm was unreachable. And `apply(_:childDelta:_:)` centralises the parent/child bookkeeping in one place so the three mutating paths — hold, release, commit — cannot drift apart on it; a side effect is that no mutating path does an optional dictionary lookup, so there are no unreachable `guard let` failure branches anywhere in the actor. Same lesson as 07-28's `AuthorityBroker` and 07-29's `ClaimVerdict`: an unreachable branch is a design smell, not a tooling artifact.

**Built: `CostEstimatorKit`.** It is the deliberate counterpart to yesterday's package. `QuotaGovernorKit` reserves against a `Cost` the caller hands it and never asks where that number came from; in the shared demo it was a literal. This computes it.

The core of it is not machine learning, it is arithmetic nobody does: **an agent loop resends its transcript on every step.** Step 1 sends the system block and the prompt; step 12 sends those plus eleven answers plus every tool result. Input grows roughly quadratically in step count while the estimate written by hand grows linearly. On the package's own twelve-step scenario the accumulating forecast is **293% of the flat one** — 191,100 input tokens against 62,400. Tool results, compaction, prompt-cache pricing and retry overhead are modelled for the same reason: each moves the answer by more than the precision anyone claims for the estimate.

Output length is the one input a plan genuinely cannot supply, so it sits behind `OutputLengthPredictor`. `FixedOutputPredictor` is deterministic — the right choice for a CI budget check or an approval screen that must show the same number twice. `EMAOutputLengthPredictor` is an actor keyed by `InputShape` (model, task kind, and the *binary magnitude* of the input, so nearby prompt sizes share history instead of every run becoming a unique key that never teaches anything).

**One decision worth recording, because it was the tempting mistake.** Reconciliation produces a residual, and there were two plausible consumers for it. The package feeds **two learners with one job each**: the predictor learns output length (sharpening the point estimate) and the calibration record learns dispersion (setting the width of the band). Signed bias is measured and *reported but never auto-applied*. Applying it would have meant two feedback loops learning from the same runs and correcting each other's corrections, and a forecast nobody could explain. The band is also the honest output shape: a point estimate for a non-deterministic quantity is a claim the package cannot back.

Money is integer microcents throughout (1e-8 of a dollar), rates in microcents per million because that is the unit vendors publish — a $3.00/M input rate is `300_000_000`, dividing to a clean 300 microcents per token with no float anywhere. No clock, no network, no Foundation in the library target.
